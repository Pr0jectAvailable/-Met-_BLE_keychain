Прошивка
Брелок делает пять вещей: выпускает в эфир анонимный ID, слушает чужие, записывает встречи, привязывается к владельцу по QR и отдаёт журнал только его телефону. SDK на выбор разработчика (nRF Connect SDK / Zephyr предпочтительнее ради переезда на свою плату; Arduino / Adafruit nRF52 допустимо для MVP). Все числа ниже — стартовые, их можно менять по итогам тестов.
Ключи и идентификаторы
Что	Размер	Где хранится	Зачем
Номер устройства, например MET-00001	—	брелок, QR, сервер	Найти брелок при привязке
K_dev, ключ анонимных ID	16 байт	брелок, сервер	Считать меняющийся ID. Не покидает брелок, владелец его не знает
K_log, K_time, K_rcpt	32 байта	считаются из K_dev, отдельно не хранятся	HKDF-SHA256(K_dev, "met-log-v1" / "met-time-v1" / "met-pair-v1"): подпись журнала, проверка времени, квитанции привязки
K_pair, код привязки	16 байт	брелок, QR, сервер	Первая привязка. После неё отключается
K_owner, ключ владельца	16 байт	брелок, телефон владельца	Синхронизация. Генерируется случайно при привязке
У каждого брелока свои ключи. Нужен скрипт прошивки на потоке: генерирует номер и ключи, записывает их в брелок, делает картинку QR и добавляет строку в CSV для бэкенда. CSV сразу шифруется публичным ключом бэкенда (age или gpg): в нём ключи всех брелоков, это самый опасный файл проекта. Открытый CSV не сохраняется на диск, не пересылается в мессенджерах и не кладётся в репозиторий.
1. Реклама («кричать»)
•	Анонимный ID = первые 16 байт HMAC-SHA256(K_dev, epoch), где epoch = floor(unix_time_UTC / 900), записанный как 4 байта big-endian. Формат обязан байт в байт совпадать с сервером — иначе сервер не узнает ни одного брелока. Для проверки нужны тестовые векторы (см. «Что сдаётся»).
•	При каждой смене ID одновременно меняется MAC-адрес (случайный private address).
•	Пакет: метка Met + версия + ID. Формат на выбор разработчика; например, manufacturer data с тестовым company ID 0xFFFF и магическими байтами — влезает в 31 байт.
•	Интервал рекламы: старт 500 мс. Мощность передатчика: старт 0 дБм. Оба параметра настраиваются.
•	Пока брелок не привязан или не знает точного времени, анонимный ID не выпускается. В непривязанном режиме брелок рекламирует свой номер для привязки.
2. Сканирование («слушать»)
•	С duty-cycle: старт — окно 600 мс каждые 10 с. Окно должно быть длиннее интервала рекламы, иначе брелоки пропускают друг друга.
•	Фильтр по метке Met, остальное (наушники, часы) игнорируется.
•	Реклама самого себя игнорируется.
3. Журнал встреч
•	Запись: ID (16 байт), время первого и последнего обнаружения, максимальный RSSI, число обнаружений.
•	Один и тот же ID, увиденный снова в пределах 2 мин, обновляет ту же запись. Склеивание разных ID одного брелока делает сервер.
•	Слабее порога RSSI не записывается. Стартовый порог выбирается по тесту дальности, цель — примерно 5–10 м в кармане.
•	Хранение во флеше (кольцевой буфер) минимум на 2 недели. Переживает перезагрузку и разряд.
Подпись записей (без неё сервер верит журналу на слово, и Android-телефон может собрать чужие ID из эфира и выдать их за журнал своего брелока):
•	У каждой записи есть seq — счётчик, который только растёт и хранится во флеше (не сбрасывается ни при перезагрузке, ни при отвязке).
•	Подпись tag = первые 16 байт HMAC-SHA256(K_log, номер устройства ‖ seq ‖ ID ‖ t_first ‖ t_last ‖ RSSI ‖ count), где K_log = HKDF-SHA256(K_dev, "met-log-v1").
•	Владелец K_dev не знает, поэтому ни подделать, ни изменить запись не может. Сервер проверяет подпись и что seq больше уже принятых. Формат полей (порядок, длины, big-endian) фиксируется в описании протокола и покрывается тестовыми векторами.
•	На nRF52840 есть аппаратный блок криптографии, на батарею это почти не влияет.
4. Часы
•	Время (UTC) принимается только подписанным сервером: брелок даёт случайное число, телефон передаёт его серверу и возвращает {время, число, HMAC(K_time, время ‖ число)}, где K_time = HKDF-SHA256(K_dev, "met-time-v1"). Телефон только связной. Иначе владелец может перевести часы вперёд, записать будущие ID своего брелока и потом воспроизвести их с телефона без самого брелока. При привязке и каждой синхронизации.
•	После полного разряда брелок не выпускает ID, пока телефон не поставит время.
•	Уход часов за неделю измерить и указать в отчёте.
5. Привязка по QR
1.	В QR: номер устройства + K_pair (например, met://pair?d=MET-00001&k=<base32>).
2.	Телефон находит брелок по номеру и подключается. Соединение шифруется средствами BLE (LE Secure Connections).
3.	Challenge-response: брелок присылает случайное число, телефон отвечает HMAC(K_pair, число). Сам K_pair по воздуху не передаётся.
4.	После проверки телефон передаёт случайный K_owner, точное время и одноразовое число от сервера (nonce). Брелок сохраняет K_owner, больше не принимает K_pair и возвращает квитанцию: receipt = HMAC-SHA256(K_rcpt, "paired" ‖ номер устройства ‖ nonce ‖ SHA256(K_owner)), где K_rcpt = HKDF-SHA256(K_dev, "met-pair-v1"). Телефон пересылает квитанцию серверу — так сервер точно знает, что привязка прошла, а не верит телефону на слово.
5.	Отвязка — только командой от владельца с одноразовым числом от сервера. Перед ней телефон выгружает журнал. Брелок стирает K_owner и журнал, возвращает квитанцию HMAC-SHA256(K_rcpt, "unpaired" ‖ номер устройства ‖ nonce) и снова принимает K_pair. Если брелок потерян, сервер отвязывает его без квитанции и помечает «нужен сброс»; найденный брелок для MVP сбрасывается перепрошивкой по USB.
Порядок с сервером (чтобы брелок и сервер не разошлись): ① приложение получает от сервера одноразовое число и резервирует брелок (сервер проверяет, что он свободен) → ② привязка по Bluetooth (шаги 1–4 выше), брелок возвращает квитанцию → ③ приложение отправляет квитанцию серверу, сервер проверяет её своим K_dev. Если шаг ② не удался, сервер снимает резерв через 10 минут. Отвязка так же: число от сервера → команда брелоку → квитанция → сервер.
6. Синхронизация (GATT)
Перед любой командой, кроме чтения версии, телефон проходит challenge-response с K_owner. UUID и форматы выбирает разработчик и описывает в документе протокола.

Безопасность
Обязательные требования даже для MVP: их дороже добавлять потом, чем сделать сразу.
1.	В эфире нет ничего постоянного. ID и MAC меняются одновременно; в пакете нет серийного номера, имени устройства и других стабильных полей. Исключение — непривязанный режим.
2.	K_dev никогда не покидает брелок по BLE, даже владельцу.
3.	K_pair и K_owner не передаются открыто. Проверка — только challenge-response (HMAC-SHA256) со свежим случайным числом от аппаратного ГСЧ.
4.	Соединение с телефоном зашифровано (LE Secure Connections) — журнал и K_owner идут по зашифрованному каналу.
5.	Защита от перебора: после 3 неверных ответов подряд — пауза, чужое соединение рвётся по таймауту.
6.	Включён APPROTECT (защита чтения) в релизной сборке, выключены отладочные логи и лишние сервисы. У клонов с USB-загрузчиком проверить, что загрузчик не отдаёт ключи.
7.	Ключи уникальны для каждого брелока — взлом одного не ломает остальные.
Дополнительно: журнал подписан брелоком, время принимается только от сервера, привязка и отвязка подтверждаются квитанцией (см. «Журнал встреч», «Часы», «Привязка по QR»). Ретрансляцию радиосигнала в реальном времени подпись не закрывает — против неё лимиты и флаги аномалий на сервере.
